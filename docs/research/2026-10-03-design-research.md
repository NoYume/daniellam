## Research question

Design research for a personal website for a student/early-career engineer targeting AI software engineering, robotics, and robotics research roles. Goal: merge a clean academic-researcher site (scannable featured research, publications with teaser videos/images, experience with company media, contact — like jimfan.me and huy-ha.github.io) with a polished designer/SWE portfolio aesthetic (like enochzhu.com, shikun.io, n3wth.com), plus personal sections (travel/everyday photo collage like Hanif Abdlh's portfolio 'shots of my experiences' section, music, interests). Research angles: (1) Concrete design teardown of each reference site — enochzhu.com (source github.com/Wavefire5201/enochzh), jimfan.me, shikun.io (template github.com/lorenmt/clarity-template), huy-ha.github.io, n3wth.com (source github.com/n3wth/n3wth), and Hanif Abdlh's portfolio: fonts, type scale, color palette, layout grid, motion/interaction, section structure, and tech stack. (2) What robotics/AI research labs, PIs, and industry recruiters (e.g., NVIDIA, robotics startups) look for on a candidate's personal website, and conventions for publication/project listings (author highlighting, venue tags, paper/code/video links, teaser videos, project pages). (3) Best 2026 framework + hosting choice for a fast, static, content-driven, image- and video-heavy personal site (Astro vs Next.js vs alternatives; GitHub Pages vs Vercel vs Cloudflare Pages), including built-in image optimization and typed content collections/MDX for publications, projects, and photos. (4) Implementation patterns and API constraints for: a hover-interactive photo collage/masonry gallery with lightbox and responsive images; a rotating full-bleed hero photo with photographer/location credit; a 'now playing'/recently-played music widget (current 2025-2026 status of Spotify Web API access restrictions vs Last.fm vs Apple Music); and muted autoplay teaser videos on research cards. (5) Performance and accessibility for media-rich dark-mode portfolio sites that use color accents: mobile Core Web Vitals, why heavy WebGL/3D landing pages hurt mobile, prefers-reduced-motion, lazy-loading video, and dark-theme contrast.

## Summary

The verified evidence supports a hybrid site. Take jimfan.me's one-page, anchor-linked structure and research anatomy: media-first featured cards, and publication rows with venue and award tags, the owner's name highlighted, and Paper/arXiv/Code/Video/BibTeX buttons (al-folio generates the same anatomy from BibTeX). Wrap that in Enoch Zhu's restrained visual system: two self-hosted fonts, a tinted dark palette with one accent shown only for interaction or live states, and a full-bleed random photo hero with credit, chosen before first paint. Enoch's 'too small, too empty' feel comes from measurable choices, not his aesthetic: 12-14px text and 14px mono section labels inside a 56rem (896px) column. A larger fluid type scale and wider media sections fix it; jimfan.me, for example, raises its root size from 16.17px to 21px on desktop. Personality can come from Hanif Abdillah's grayscale-to-color 'Shots of my experience' grid with a keyboard lightbox, and from n3wth-style SVG line art carrying colored pulses. That line art uses no WebGL, and its 'Google colors' are actually Apple iOS system tints. Avoid the measured failures: about 14.6 MB of autoplaying GIF/MP4 teasers on jimfan.me, unoptimized hover-only photos in an empty client-rendered shell on Hanif's site, and WebGL on the mobile landing path. The strongest stack precedent is static prerendering with zod-typed content collections on Cloudflare plus one tiny Worker for live data such as a Last.fm feed. No direct framework comparison, Spotify API status, Core Web Vitals measurement or recruiter evidence survived verification. The only verified reader guidance, from Michigan Robotics faculty on PhD applications, favors detailed project stories inside a coherent, research-led track record.

### 6. Enoch's hero is the best-documented pattern for a full-bleed rotating photo with a credit that stays fast on mobile. The hero is a full-viewport section (h-svh). app.html runs an inline script over the photo set mountain/forest-road/blossom/gapstow-bridge/snow-peak/red-flowers. ### 8. The n3wth graphics the user liked, 'white bodies with colors flowing through them', are inline SVGs with no WebGL. They are cheap and accessible. 1px lines at 40% opacity carry 1.5px gradient pulses, which a requestAnimationFrame loop moves on its own schedule. The loop pauses off-screen, in hidden tabs and under reduced motion. That makes the effect an easy-to-reproduce signature that can carry the site's extra color.

Confidence: high. Vote: 3-0 (claim 6).

SectionStory.tsx has one drawing per section: work, art, thinking, projects, library and contact. The wrapper is aria-hidden and the SVG is focusable=false. sectionStory.css draws base paths in currentColor at 1px, vector-effect: non-scaling-stroke, opacity .4. Pulses are 1.5px strokes filled with a linearGradient between two neighboring tokens from cyan/green/yellow/red; each pulse keeps a fixed pair. In storyInteractions.ts each pulse lasts 3.5-7 s, followed by an 18-50 s pause. When lit light crosses another line, it starts a chain-reaction transfer pulse (2.5-5 s, at most 5 deep, 2 s cooldown per line). Nothing responds to cursor, hover or scroll, and pointer-events is none. Motion pauses via IntersectionObserver, visibilitychange and matchMedia('(prefers-reduced-motion: reduce)'), leaving a still composition. Sizing is min(135vw, 88svh) below 1024px, and min(78vw, 112svh) at left:70% from 1024px up. The feature was added 2026-09-22 and last changed 2026-10-01, so it is still moving fast. The lines are white only in dark mode. The n3wth homepage is a separate WebGL scene, the part the user disliked. Implication (synthesis): draw robotics-flavored line art per section, such as arm linkages, trajectories or a gripper. Drive the pulses with the site's own accent set instead of Apple tints, and keep them autonomous and paused off-screen.

Sources: https://github.com/n3wth/n3wth

### 10. The references give a concrete do/don't list for media performance. jimfan.me autoplays about 14.6 MB of GIF posters and MP4 teasers with no preload control, and some videos are encoded at up to 1080p for 640x360 slots. Hanif ships full-size photos with no lazy loading, hides color behind hover and serves an empty HTML shell. Enoch shows the fixes: a preloaded responsive poster as the LCP element, WebGL loaded only after user intent, and exits for reduced motion and missing WebGL. n3wth's line art adds pausing off-screen, in hidden tabs and under reduced motion.

Confidence: high. Vote: 3-0 (claims 14, 9, 8, 6); 2-1 (claim 3).

jimfan.me: four <video autoplay muted loop playsinline> elements with no preload attribute. Their posters are animated GIF89a files (36-72 frames) totaling 4,029,872 bytes, and the MP4s total 10,591,708 bytes. VIMA is encoded at 1920x1080 and MineDojo at 800x450, both shown in 640x360 slots. Its publication thumbnails, by contrast, are lazy-loaded 500x281 WebP, which is the right pattern. Hanif: no srcset, no lazy loading and no Cloudinary transforms. Color shows only on hover, so touch users never see it, and the client-rendered shell is empty without JS. Implication (synthesis): for teaser videos, use static WebP/AVIF posters instead of GIFs, and MP4 (optionally WebM) encoded at display size. Set preload=none or metadata, play and pause with IntersectionObserver, never autoplay under reduced motion, and keep controls available. For photos, use responsive srcsets with explicit dimensions and lazy-load below the fold. Keep WebGL off the mobile landing path. No Core Web Vitals field data (LCP/INP/CLS) was measured or verified for any reference.

### astro.build

Source URLs: https://astro.build/blog/astro-7/

- Astro 7.0 (released June 22, 2026) is mainly a build-speed release. The .astro compiler was rewritten in Rust, and Markdown/MDX now goes through a Rust pipeline. A queue-based renderer is now the default, and Astro moved to Vite 8 with the Rust-based Rolldown bundler. Astro's own benchmarks show builds 15-61% faster. Those benchmarks ran on an Apple M4 Pro MacBook Pro using sites of 308 to 13,275 pages. The biggest gains are on sites heavy in .astro compilation and Markdown, and a footnote says static pages see little benefit from queued rendering. Implication: for a small static personal site, build speed should not decide the framework. The post announces no changes to image optimization (astro:assets, Image/Picture) or to build-time content collections, so it is not a source for those features.
  - Quote: "Astro 7 is here! This release is all about speed. The .astro compiler has been rewritten in Rust. Markdown and MDX processing now runs through a new Rust-powered pipeline. The rendering engine has been replaced with a faster queue-based approach. Together with Vite 8 and its new Rolldown bundler, Astro 7 builds are 15-61% faster in our benchmarks. ... Sites where .astro compilation and Markdown processing make up a larger share of the build see the biggest gains, since those are exactly the parts that moved to Rust. ... Static pages wouldn’t see much savings."
- Astro 7 replaces the old default Markdown/MDX pipeline (unified/remark/rehype) with Satteri, a Rust processor built on pulldown-cmark and Oxc. Satteri has these built in: GFM (on by default), smart punctuation, heading IDs, YAML/TOML frontmatter, superscript/subscript, wikilinks, math and container directives. Per the post's config example, non-default features such as math and directives are switched on with a `features` option. Any project or ported template that relies on remark or rehype plugins has to set up the unified processor from @astrojs/markdown-remark explicitly. This matters for MDX-driven publication and project content.
  - Quote: "Astro 7 replaces the default Markdown and MDX pipeline with Sätteri, a Rust-powered processor created by Astro core team member Erika. ... If you depend on remark or rehype plugins, the unified-based pipeline is still available via @astrojs/markdown-remark"
- Astro 7's new Rust .astro compiler (built on oxc and Lightning CSS) is only 'mostly backwards compatible'. It no longer silently corrects HTML, and unclosed tags or unterminated attributes are now errors. Whitespace between elements is collapsed the way JSX does it, so a newline between inline elements no longer renders a space; you need an explicit {' '} instead. Implication: themes and templates written for earlier Astro versions can fail to compile or lose spacing on Astro 7. Inline markup split across lines, such as publication author lists, is especially at risk.
  - Quote: "The compiler is a full rewrite of our previous Go-based compiler that is mostly backwards compatible, except for: ... Whitespace between elements is now collapsed following JSX conventions, matching the behavior of React and other JSX-based frameworks. For example, newlines between inline elements no longer produce a visible space"
- Route caching is now stable in Astro 7 and applies to on-demand-rendered responses. It provides Astro.cache.set with maxAge/swr/tags, declarative routeRules, cache.invalidate by tag or path, and a built-in memoryCache provider. Astro 7 also adds experimental CDN cache providers for Netlify, Vercel and Cloudflare (cacheNetlify, cacheVercel, cacheCloudflare), each imported from its adapter's /cache entrypoint. With these, cache hits are served from the edge without calling the server function. GitHub Pages is not mentioned. Implication: this only matters for server routes, such as a cached 'now playing' music-API proxy on Vercel, Netlify or Cloudflare, and has no effect on a fully static build.
  - Quote: "When route caching shipped in Astro 6, it came with a single in-memory provider to use with the Node adapter. Astro 7 adds experimental CDN providers for Netlify, Vercel, and Cloudflare. Rather than storing responses in memory, these providers push your caching directives down to the host’s edge network, for even faster responses. Cache hits are then served straight from the CDN, without invoking your server function at all."
- Astro 7 adds dev tooling designed for AI agents. `astro dev --background` runs the dev server as a managed background process. A lockfile prevents duplicate servers, `astro dev status|stop|logs` manage it, and a /_astro/status health endpoint reports its state. When Astro detects it is running inside an AI coding agent, it turns on background mode and JSON logging automatically. `astro dev --json` or logHandlers.json() give structured logs without an agent. This is relevant if the site is built with an AI coding agent such as Claude Code.
  - Quote: "Astro 7 adds astro dev --background, which starts the dev server as a managed background process. Astro can also detect when it’s running inside an AI agent and enable background mode automatically, so no flags are needed in agent workflows."

### docs.astro.build

Source URLs: https://docs.astro.build/en/guides/images/, https://docs.astro.build/en/guides/deploy/cloudflare/

- Astro only optimizes local images stored under src/. Files in public/ are copied to the build as-is and are never processed or optimized. The same page also says responsive images are not supported for public/ images. For a photo-heavy portfolio (collage, hero rotation), the photos therefore need to live in src/ (e.g. src/assets or next to content entries) to get optimization.
  - Quote: "We recommend that local images are kept in `src/` when possible so that Astro can transform, optimize, and bundle them. Files in the `public/` directory are always served or copied into the build folder as-is, with no processing."
- The built-in <Image /> component (astro:assets) can change the dimensions, file type and quality of a local image or of a remote image from an authorized domain. For prerendered (static) pages this happens at build time. The page's example converts a 1600x900 PNG to .webp and outputs width/height, loading="lazy" and decoding="async". Writing the dimensions out prevents Cumulative Layout Shift (CLS).
  - Quote: "`<Image />` can transform a local or authorized remote image's dimensions, file type, and quality for control over your displayed image. This transformation happens at build time for prerendered pages. ... The resulting `<img>` tag includes `alt`, `loading`, and `decoding` attributes and infers image dimensions to avoid Cumulative Layout Shift (CLS)."
- Since astro@5.10.0, giving <Image /> or <Picture /> a `layout` (constrained, full-width or fixed) makes Astro generate the srcset and sizes attributes automatically. Setting image.layout globally applies this to every image component and to Markdown ![]() images. The trade-off: each responsive image becomes several files of different sizes. On prerendered pages these files are generated at build time, which can make builds longer when there are many images.
  - Quote: "With the layout property applied to the `<Image />` or `<Picture />` components, Astro will automatically generate the required `srcset` and `sizes` values for your images, and apply the necessary styles to ensure they resize correctly. ... For prerendered pages, this happens during the build and may increase the build time of your project, especially if you have a large number of images."
- Content collection schemas provide an image() helper. It validates a frontmatter image path, given relative to the entry file, and imports it as image metadata. That metadata can be passed straight to <Image />, <img> or getImage(). The example schema is: schema: ({ image }) => z.object({ cover: image(), ... }). This allows typed collections (e.g. publications with teaser images, projects, photos) whose images get the same optimization.
  - Quote: "The `image` helper for the content collections schema lets you validate and import the image."
- Sharp is Astro's default image service. The docs give Cloudflare as an example of an adapter that does not support Sharp. With such an adapter, the documented fallback is passthroughImageService(), which performs no image transformation. Only CLS prevention, the required alt attribute and the same authoring API remain. Hosting choice therefore affects image optimization when deploying through an adapter. Per the same page, prerendered pages are transformed at build time.
  - Quote: "If your adapter does not support Astro's built-in Sharp image optimization (e.g. Cloudflare), you can configure a no-op image service to allow you to use the `<Image />` and `<Picture />` components. Note that Astro does not perform any image transformation and processing in these environments."
- In 2026, Astro's official Cloudflare guide covers deployment only to Cloudflare Workers (Workers Static Assets), not Cloudflare Pages. It passes on Cloudflare's recommendation that new projects use Workers and points existing Pages projects to a migration guide. The separate 'Cloudflare Pages' section was deleted from the guide on 2026-03-18 (withastro/docs commit b24695b, PR #13466, 'remove CF Pages workaround'). A new site on Cloudflare is therefore expected to be set up as a Worker with static assets, not a Pages project.
  - Quote: "Cloudflare recommends using Cloudflare Workers for new projects. For existing Pages projects, refer to Cloudflare’s migration guide and compatibility matrix."
- A fully static (prerendered) Astro site can be deployed to Cloudflare Workers without the @astrojs/cloudflare adapter, which is needed only for on-demand rendering. The static setup is: install Wrangler, write wrangler.jsonc by hand with only name, compatibility_date and assets.directory "./dist", then run `npx astro build && npx wrangler deploy`, which returns a preview URL. (Scope note: the page does not mention image optimization or image services on Cloudflare at all.)
  - Quote: "If your site uses on-demand rendering, install the @astrojs/cloudflare adapter. [...] Running astro add cloudflare will create this for you; if you are not using the adapter, you’ll need to create it yourself."
- Cloudflare Workers Builds can build and deploy the site on every git push. In the dashboard, go to Compute > Workers & Pages > Create application, import the repository, set the build command to `npx astro build` and the deploy command to `npx wrangler deploy`, then choose Save and Deploy. The site can then be previewed at a workers.dev subdomain.
  - Quote: "You can also use a CI/CD system such as Workers Builds to automatically build and deploy your site on push."
- Server-side (on-demand) Astro code on Cloudflare runs in the Cloudflare Workers runtime, not Node.js. This matters if the site adds an API route, for example a server-side proxy for a now-playing music widget. The on-demand wrangler.jsonc sets "main": "@astrojs/cloudflare/entrypoints/server" and compatibility_flags ["nodejs_compat", "global_fetch_strictly_public"]. The build can fail with 'Could not resolve "XXXX"' when a server-side package imports a Node.js built-in that the runtime does not support. In that case you need a package that uses node:* imports, or a different package.
  - Quote: "This means that a package or import you are using in the server-side environment is not compatible with the Cloudflare runtime APIs."
- For Astro sites served as Workers static assets, a custom 404 page appears only if wrangler.jsonc sets "not_found_handling": "404-page" under assets.
  - Quote: "For Workers projects, you will need to set not_found_handling if you want to serve a custom 404 page."

### nextjs.org

Source URLs: https://nextjs.org/docs/app/guides/static-exports

- Next.js (docs v16.3.8, last updated Aug 2026) can produce a fully static site. Setting `output: 'export'` in next.config.js makes `next build` write per-route HTML plus CSS/JS assets to an `out` folder. Any static web server can host that folder without a Node.js server, and Next.js provides an official GitHub Pages deploy template (github.com/nextjs/deploy-github-pages).
  - Quote: "Since Next.js supports this static export, it can be deployed and hosted on any web server that can serve HTML/CSS/JS static assets. [...] After running `next build`, Next.js will create an `out` folder with the HTML/CSS/JS assets for your application. [...] To deploy to GitHub Pages, use our template to create a new project or as a reference for configuring an existing project."
- Static export does not support Next.js's built-in image optimization: the docs list next/image with the default loader as an unsupported feature. To optimize images with next/image in a static export, you must configure a custom loader (`images: { loader: 'custom', loaderFile }`) that sends resizing and format conversion to an outside service such as Cloudinary. A statically hosted, image-heavy Next.js site therefore gets no image optimization from the framework itself.
  - Quote: "Image Optimization through `next/image` can be used with a static export by defining a custom image loader in `next.config.js`. For example, you can optimize images with a service like Cloudinary [...] Features that require a Node.js server, or dynamic logic that cannot be computed during the build process, are not supported: [...] Image Optimization with the default `loader`"
- Static export cannot use any Next.js feature that needs a Node.js server or logic run per request. The docs list these as unsupported: Dynamic Routes with `dynamicParams: true` or without `generateStaticParams()`, Route Handlers that rely on Request, Cookies, Rewrites, Redirects, Headers, Proxy, Incremental Static Regeneration, Image Optimization with the default loader, Draft Mode, Server Actions and Intercepting Routes. Using any of them causes an error in `next dev`. As a result, dynamic content pages such as /projects/[slug] must be listed at build time with generateStaticParams(), and server logic that runs per request, such as an API proxy that holds a secret key, cannot run inside the export.
  - Quote: "If you need to read dynamic values from the incoming request, you cannot use a static export. [...] Features that require a Node.js server, or dynamic logic that cannot be computed during the build process, are not supported"
- In a static export, Server Components and their fetch() calls run only during `next build`, as in traditional static-site generation, so their data is fixed at build time. Data that must be current when someone views the page, such as a live 'now playing' music widget, has to be fetched in the browser by a Client Component (the docs suggest SWR). Browser-only APIs (window, localStorage, navigator) must be accessed only on the client, because Client Components are also prerendered at build time.
  - Quote: "When you run `next build` to generate a static export, Server Components consumed inside the `app` directory will run during the build, similar to traditional static-site generation. [...] If you want to perform data fetching on the client, you can use a Client Component with SWR to memoize requests. [...] Because Web APIs like `window`, `localStorage`, and `navigator` are not available on the server, you need to safely access these APIs only when running in the browser."
- A Next.js static export still ships client-side JavaScript for SPA-style routing. Besides static HTML for the first page load, it outputs a 'static payload for client navigation between routes', and route changes happen in the browser like a traditional SPA. The docs' performance claim (per-route HTML avoids loading unnecessary JS and reduces bundle size) compares only against a strict SPA, not against output with zero JavaScript.
  - Quote: "By breaking a strict SPA into individual HTML files, Next.js can avoid loading unnecessary JavaScript code on the client-side, reducing the bundle size and enabling faster page loads. [...] The resulting component will be rendered into static HTML for the initial page load and a static payload for client navigation between routes. [...] Since route transitions happen client-side, this behaves like a traditional SPA."

### svelte.dev

Source URLs: https://svelte.dev/docs/kit/images

- SvelteKit's official @sveltejs/enhanced-img plugin processes images at build time. It outputs smaller formats (AVIF/WebP), adds intrinsic width/height automatically to prevent layout shift, generates several sizes for different devices, and strips EXIF metadata. It works in any Vite-based project, not only SvelteKit.
  - Quote: "It provides plug and play image processing that serves smaller file formats like `avif` or `webp`, automatically sets the intrinsic `width` and `height` of the image to avoid layout shift, creates images of multiple sizes for various devices, and strips EXIF data for privacy. It will work in any Vite-based project including, but not limited to, SvelteKit projects."
- enhanced-img can only optimize image files that are on the build machine at build time. Images served from a database, CMS or backend need a CDN approach instead. The first build is slower because the images are transformed, and the output is cached in ./node_modules/.cache/imagetools so later builds are fast.
  - Quote: "As a build plugin, `@sveltejs/enhanced-img` can only optimize files located on your machine during the build process. If you have an image located elsewhere (such as a path served from your database, CMS, or backend), please read about loading images dynamically from a CDN. [...] Building will take longer on the first build due to the computational expense of transforming images. However, the build output will be cached in `./node_modules/.cache/imagetools` so that subsequent builds will be fast."
- The docs describe a trade-off between build-time and CDN image optimization. A CDN can choose the format from the User-Agent header, so a plain <img> is enough, while build-time optimization has to emit <picture> elements with multiple sources. CDNs that generate images lazily (on first request) can hurt performance on low-traffic sites whose images change often.
  - Quote: "Building HTML to target CDNs allows using an `<img>` tag since the CDN can serve the appropriate format based on the `User-Agent` header, whereas build-time optimizations must produce `<picture>` tags with multiple sources. Finally, some CDNs may generate images lazily, which could have a negative performance impact for sites with low traffic and frequently changing images."
- A folder of static images, such as a photo gallery, can be processed in one batch with Vite's import.meta.glob and the `enhanced` custom query. When a `sizes` attribute is given, enhanced-img fills srcset with smaller versions, and the smallest one it generates automatically is 540px wide (custom widths can be set with the ?w= query). Without `sizes`, it generates only a standard-resolution and a HiDPI version.
  - Quote: "You can also use Vite's `import.meta.glob`. Note that you will have to specify `enhanced` via a custom query [...] If `sizes` is specified, `<enhanced:img>` will generate small images for smaller devices and populate the `srcset` attribute. The smallest picture generated automatically will have a width of 540px. [...] If `sizes` is not provided, then a HiDPI/Retina image and a standard resolution image will be generated."
- For the LCP image (for example a full-width hero photo), the docs recommend setting fetchpriority="high" and not using loading="lazy". They also recommend specifying `sizes` for images much wider than a mobile screen (about 400px) and giving images width/height so the browser reserves space and avoids CLS. They also advise supplying source images at 2x their display width for HiDPI screens.
  - Quote: "For images which are much larger than the width of a mobile device (roughly 400px), such as a hero image taking the width of the page design, specify `sizes` so that smaller images can be served on smaller devices. - For important images, such as the largest contentful paint (LCP) image, set `fetchpriority="high"` and avoid `loading="lazy"` to prioritize loading as early as possible."

### developer.spotify.com

Source URLs: https://developer.spotify.com/documentation/web-api/references/changes/february-2026, https://developer.spotify.com/blog/2026-06-18-refresh-token-expiration, https://developer.spotify.com/documentation/web-api/concepts/quota-modes

- After Spotify's February 2026 Web API changes, the endpoints a personal now-playing or recently-played widget needs are still available: GET /me/player/currently-playing, GET /me/player/recently-played, GET /me/player and GET /me/top/{type}. The page lists them under 'Endpoints still available'. The field removals listed elsewhere on the page still apply to their responses.
  - Quote: "These endpoints remain available, but the changes mentioned above still apply to them. ... Get Currently Playing Track (GET /me/player/currently-playing) – Retrieves the item currently being played. ... Get Recently Played Tracks (GET /me/player/recently-played) - Get tracks from the current user's recently played tracks. ... Get User's Top Items (GET /me/top/{type}) – Retrieves the user's top artists or tracks over a given time range."
- The February 2026 field removals apply to content objects in every response, including the track and album objects in player responses. Tracks lose popularity, available_markets and linked_from. Albums lose label, popularity and album_group. Artists lose followers and popularity. This means a widget cannot show popularity or record-label metadata. The page notes that the external_ids removal was later reverted, citing the March 2026 changelog.
  - Quote: "The following content types and their objects are present in most responses - these changes apply for their occurances in all responses. ... [REMOVED] popularity — The popularity of the track. The value will be between 0 and 100, with 100 being the most popular. ... [REMOVED] external_ids — Known external IDs for the track. Reverted — See March 2026 changelog. ... [REMOVED] label – The label associated with the album."
- Spotify removed the endpoints for reading other users' public profiles and playlists. GET /users/{id} and GET /users/{id}/playlists are gone. Playlist objects now include track items only for the authenticated user's own playlists, and other playlists return metadata only. So a site's music section can list a playlist's tracks only if the playlist belongs to the site owner's authenticated account.
  - Quote: "[REMOVED] Get User's Playlists (GET /users/{id}/playlists) – Get a list of the playlists owned or followed by a Spotify user. ... [REMOVED] Get User's Profile (GET /users/{id}) – Get public profile information about a Spotify user. ... Will only return an items object for the user's playlist, other playlists will only provide metadata (not the contents of the playlist) in the response."
- The changes are tied to Spotify's 6 February 2026 blog post on developer access and platform security. The docs sidebar titles the companion migration guide 'Migration: February 2026 Dev Mode Changes', which suggests the restrictions target Development Mode apps, the mode a single-owner personal-site widget would normally use. The page itself does not mention development mode, Premium or quota limits. The sidebar also lists later changelogs for March, May and July 2026, so the current status should be checked against those.
  - Quote: "These changes are related to [this](/blog/2026-02-06-update-on-developer-access-and-platform-security) blog post. ... [sidebar link] Migration: February 2026 Dev Mode Changes"
- Spotify removed the batch and catalog-discovery endpoints. These include Get Several Tracks/Albums/Artists, Get Artist's Top Tracks, Get New Releases and the browse categories. Single-item lookups such as GET /tracks/{id} remain, so a hand-picked 'favorite albums or tracks' section must fetch one item per request or store the metadata statically. Search was also limited to at most 10 results per request, down from 50.
  - Quote: "[REMOVED] Get Several Tracks (GET /tracks) – Get Spotify catalog information for multiple tracks based on their Spotify IDs. ... [REMOVED] Get Artist's Top Tracks (GET /artists/{id}/top-tracks) – Get Spotify catalog information about an artist's top tracks by country. ... Get Track (GET /tracks/{id}) – Retrieves metadata for a single track."
- Spotify refresh tokens from user-authorization flows now require the user to sign in again after 6 months, and Spotify tells developers to stop treating a stored refresh token as valid forever. This breaks the common personal-site 'now playing' pattern of creating one refresh token and storing it as a fixed secret or env var. That token now has to be regenerated at least every 6 months.
  - Quote: "Refresh tokens issued to apps registered on Spotify for Developers will now require reauthentication after 6 months. Once a refresh token expires, your app must send the user through the sign-in flow to obtain a new one. ... Do not assume refresh tokens are permanent. Any code that treats a stored refresh token as indefinitely valid will need to be updated."
- Enforcement started right away (June 18, 2026) for newly registered apps and on July 20, 2026 for existing apps. Once enforcement starts, existing refresh tokens older than 6 months are invalidated the next time they are used. So as of late 2026, every app registered on Spotify for Developers, including hobby and personal-site apps, has the 6-month limit.
  - Quote: "New apps: affected as of today. Existing apps: affected from July 20, 2026. ... Once enforcement begins for existing apps, refresh tokens older than 6 months will be invalidated on their next use. Users will see the sign-in prompt and will need to re-authorize your app."
- The 6-month lifetime is fixed and counts from the user's original authorization. Refreshing access tokens, for example a widget that polls the API constantly, does not reset or extend it. Only a new authorization by the user starts a fresh 6-month window.
  - Quote: "Refreshing an access token does not reset or extend the refresh token's 6-month lifetime. The lifetime is measured from the moment of the user's original authorization. If the user re-authorizes your app, a fresh 6-month lifetime begins."
- The expiration only covers tokens issued on behalf of a user (Authorization Code and Authorization Code with PKCE flows). The Client Credentials flow is not affected. Not stated in the post (check against the Web API reference): endpoints for a user's own data, like currently-playing and recently-played, need user-authorized tokens, so a now-playing widget probably can't avoid the limit by switching to Client Credentials.
  - Quote: "Does this affect Client Credentials flow? No. This only applies to tokens issued on behalf of a user (Authorization Code and Authorization Code with PKCE flows)."
- When a refresh token has expired, POST https://accounts.spotify.com/api/token returns 400 Bad Request with the error invalid_grant, and the app should not retry. Refresh tokens don't include an issue date, so developers have to save the authorization date themselves to know when expiry is coming. For a personal widget, that means catching invalid_grant so the widget fails gracefully, and setting a reminder to re-authorize.
  - Quote: "When a refresh token expires, the Spotify token endpoint (POST https://accounts.spotify.com/api/token) will return a 400 Bad Request response with an invalid_grant error. ... Refresh tokens do not expose an issuance timestamp. If you need to track expiration, store the authorization timestamp in your own database when the user first authorizes your app."
- A Spotify Web API app in development mode can be used by at most 5 authenticated Spotify users, and each must be manually added to the app's allowlist in the Developer Dashboard. The page says non-allowlisted users who log in get 403 errors on API calls. Implication: a personal-site now-playing widget has to use only the site owner's own token, server-side, and cannot have visitors sign in.
  - Quote: "Up to 5 authenticated Spotify users can use an app that is in development mode — so you can share your app with beta testers, friends, or with fellow developers who are working on the app. Each Spotify user who installs your app will need to be added to your app's allowlist before they can use it."
- Development-mode Spotify apps only work if the app owner has a Spotify Premium account. A Spotify-powered now-playing widget therefore needs the site owner to keep a paid Premium subscription, a cost and dependency that Last.fm-based widgets do not have.
  - Quote: "Note: The app owner must have a Spotify Premium account for apps in development mode to function."
- Since May 15, 2025, Spotify accepts extended quota mode applications (the mode that allows unlimited users) only from organizations, not individuals. Requirements include a legally registered business and at least 250k monthly active users. An individual student's personal site cannot realistically get out of development mode.
  - Quote: "Please note that as of May 15th 2025, Spotify only accepts applications from organizations (not individuals). ... Established Business Entity (legally registered business or organisation) ... Maintaining a minimum of active users (at least 250k MAUs)"
- Spotify presents development mode as suitable for apps that access or manage data in a single Spotify account. That fits a personal now-playing or recently-played widget, which reads only the site owner's account, without needing extended quota.
  - Quote: "This mode is perfect for apps that are under construction and apps that have been built for accessing or managing data in a single Spotify account."
- Development-mode apps fall under a request quota per developer account, separate from rate limits, and the limits are unpublished and subject to change. Going over it returns HTTP 429 with reason "QUOTA_EXCEEDED". Implication: a site widget should cache Spotify responses server-side, not call the API on every page view.
  - Quote: "Spotify's Web API has a quota system that limits the number of requests made through development mode apps that belong to a single developer account. Note that this is different from rate limits. ... The specific groupings and limits are subject to change. When the quota has been exceeded, the Web API returns a 429 Too Many Requests response"

### last.fm


- Last.fm's user.getRecentTracks returns a user's recently scrobbled tracks and, if the user is listening right now, includes the current track flagged with a nowplaying="true" attribute. One call can therefore drive both the 'now playing' and 'recently played' states of a music widget.
  - Quote: "Get a list of the recent tracks listened to by this user. Also includes the currently playing track with the nowplaying="true" attribute if the user is currently listening."
- user.getRecentTracks needs no user authentication (no session key or OAuth). Its only required parameters are a Last.fm API key and the target Last.fm username.
  - Quote: "user (Required) : The last.fm username to fetch the recent tracks of. ... api_key (Required) : A Last.fm API key. ... This service does not require authentication."
- The method is a simple GET on the /2.0/ REST endpoint. Adding format=json returns JSON instead of the default XML, so a static site's JavaScript or a serverless function can consume it directly.
  - Quote: "JSON: /2.0/?method=user.getrecenttracks&user=rj&api_key=YOUR_API_KEY&format=json"
- Results are paginated, with 'limit' defaulting to 50 and capped at 200 per page. Optional 'from'/'to' UNIX UTC timestamps filter by time range, and 'extended=1' adds extended artist data plus whether the user loved each track.
  - Quote: "limit (Optional) : The number of results to fetch per page. Defaults to 50. Maximum is 200. ... extended (0|1) (Optional) : Includes extended data in each artist, and whether or not the user has loved each track"
- The API enforces per-IP rate limiting (error 29) and can suspend API keys (error 26), but this page gives no numeric rate limit. Polling frequency and caching for a now-playing widget have to be set conservatively without a documented threshold.
  - Quote: "26 : Suspended API key - Access for your account has been suspended, please contact Last.fm ... 29 : Rate limit exceeded - Your IP has made too many requests in a short period"

### nicholasgriffin.dev

Source URLs: https://nicholasgriffin.dev/blog/building-a-recently-played-widget-with-apple-music

- Apple Music recently-played data for a personal-site widget can be fetched server-side with one GET request to https://api.music.apple.com/v1/me/recent/played/tracks?limit=N. The request sends two headers: 'Authorization: Bearer <developer token>' and 'Music-User-Token: <user token>'. The endpoint returns recently played tracks. It is not a live 'now playing' feed.
  - Quote: "This isn't super complicated, really it's just a GET call to the API with two headers: ... `https://api.music.apple.com/v1/me/recent/played/tracks?limit=${limit}` ... Authorization: `Bearer ${musicKitToken}`, 'Music-User-Token': userToken,"
- The Apple Music API needs a 'Developer Token'. This is a JWT signed with ES256 from your Apple Developer Team ID, a MusicKit key identifier and a private key, and it can last at most 6 months (15,777,000 seconds). Getting these credentials requires a paid Apple Developer membership, which the author pays for only to run the widget.
  - Quote: "First need to create a "Developer Token", this is a JWT that you will generate using your team ID, a MusicKit identifier and private key. ... sign a token with a 6 month expiry (the max available). ... Yeah, I am totally only really paying for Apple Developer so I can display a widget on my homepage...."
- The Music-User-Token can only be obtained by the user logging in interactively through Apple's MusicKit JS SDK in a browser page, and Apple offers no React SDK for this. For a single-owner widget, the author logs in once on a standalone HTML page and stores the token in environment variables. He says this manual step has to be redone about every 6 months if the expiry stays the same. That makes Apple Music the highest-friction option compared with a simple API key.
  - Quote: "we need to get a user token which you can only get by the user authenticating with your frontend. You have to load Apple MusicKit SDK on your page (and yes, there's no React SDK for this for some unknown reason...). ... I then stored this value in my environment variables for use with the API. This will have to be done once every 6 months if you keep the expiry the same."
- Each track in the recently-played response includes album and artist names, an artwork URL with bgColor and textColor1-4 values, durationInMillis and preview audio URLs. That is enough to color the widget from the album art and play previews. The response type shown in the post has no played-at timestamp field.
  - Quote: "That provides us with basically all we need in order to display the items in the widget but also provide the ability to play previews of the tracks and set some colour styles to match the styles of Apple Music itself."
- The author's earlier widget showed his Spotify listening through Last.fm instead of Spotify's own API, because Last.fm's API was easier to work with at the time. That is evidence for Last.fm as the simpler proxy for showing Spotify listening. The post says nothing specific about Spotify Web API access restrictions.
  - Quote: "For some time now I've had a widget on the right side of the hero that displays my most recently played tracks from Spotify (or rather LastFM because their API was easier to work with at the time)."

### webkit.org

Source URLs: https://webkit.org/blog/17758/when-will-css-grid-lanes-arrive-how-long-until-we-can-use-it/

- As of Jan 22, 2026, native CSS masonry using the finalized `display: grid-lanes` syntax was available only in Safari Technology Preview; Chrome, Edge and Firefox were still working on their implementations. The article also says to watch Safari release notes for when it reaches Safari beta, so it had not shipped there either. A photo collage built then could not rely on native CSS masonry without a fallback. This status is eight months old as of Oct 2026 and should be re-checked against current browser support data.
  - Quote: "Currently, the finalized syntax for Grid Lanes is available in Safari Technology Preview. Edge, Chrome and Firefox have all made significant progress on their implementations, so it’s going to arrive sooner than you think."
- WebKit's preferred way to use masonry now is a pure-CSS fallback. Declare `display: grid;` and then immediately `display: grid-lanes;`. Browsers that don't recognize grid-lanes ignore the second line and keep a normal CSS Grid. Then, inside `@supports not (display: grid-lanes)`, give every image `aspect-ratio: 1` plus `object-fit: cover` so all tiles are the same cropped size. This needs no JavaScript for layout.
  - Quote: "perhaps the best approach is to write your code so that Grid Lanes is used when supported, and another layout mode in CSS is used as the fallback. This avoids using JavaScript for layout, while still delivering the newer layout to the users who do have support."
- CSS Multicolumn has worked in browsers for decades and is a no-JS way to get a masonry-like look, but its content flows differently from Grid Lanes. That changes keyboard tab/focus order and how easily people can scan the items. This matters for accessibility in a gallery where each photo is a focusable lightbox trigger.
  - Quote: "Multicolumn and Grid Lanes can result in very similar-looking layouts. They are fundamentally different, however, in the way content flows. These differences impact the order of what comes into focus when tabbing through content, readability / scanability, and user experience. So consider carefully."
- If a JavaScript masonry library such as Masonry.js is used as a polyfill, load it only when `CSS.supports('display', 'grid-lanes')` returns false. Browsers with native support then never download or run the script, which is a performance gain that grows as support spreads.
  - Quote: "It’s important to conditionally load the JS library only if the browser doesn’t support Grid Lanes. There’s no reason to have all users download and run the JS file when some percent don’t need it."
- Chrome and Edge 140 added masonry behind a flag in July 2025, using a different syntax from the Safari/Firefox proposal. As of Jan 2026, Chromium engineers at Edge were updating it to the finalized syntax. Firefox's flagged/Nightly version still used the older `grid-template-*: masonry` syntax. So none of the flagged versions in Chromium or Firefox matched `display: grid-lanes` at that point.
  - Quote: "A variation for how masonry layouts could work in CSS landed in Chrome and Edge 140 behind a flag in July 2025. Rather than implementing the same syntax as Safari and Firefox, Chromium experimented with an alternative proposal. … With key syntax decisions now finalized, Chromium engineers at Edge are updating their implementation."

### medienbaecker.com

Source URLs: https://medienbaecker.com/articles/dialog-view-transitions

- A morph animation from a grid thumbnail to a full-size lightbox can be built with only native browser APIs, without FLIP code or a JS animation library. Wrap the native <dialog>'s showModal() call in document.startViewTransition(), and hand a shared view-transition-name from the grid image to the dialog's image so the browser morphs one into the other. The author clones the card into the dialog instead of moving it, and hides the grid original with visibility: hidden. This keeps the gallery or masonry layout from reflowing and gives the closing animation a target to return to.
  - Quote: "For same-document view transitions, you wrap a DOM change in document.startViewTransition(), and the browser snapshots before and after. Elements with matching view-transition-name values get morphed between states. ... In this case, the dialog’s showModal() is our DOM change. ... I clone the card instead of moving it. The original stays in the grid (hidden with visibility: hidden). This keeps the layout intact and gives the closing transition somewhere to animate back to."
- Instead of building this by hand, you can use the open-source Parvus lightbox library. It has had view transitions built in since its 3.0.0 release and also provides gallery navigation (galleries and prev/next arrows). The author recommends it for an accessible lightbox; this recommendation was added in the 19 Dec 2025 update.
  - Quote: "I just realised my favourite lightbox library Parvus has view transitions built in since its 3.0.0 release. If you’re looking for an accessible lightbox, using Parvus might be a better idea than writing all of this from scratch. You’ll even get galleries and arrows!"
- Calling showModal() on a native <dialog> puts it on the top layer and traps focus, with no extra code. The <dialog> element works across browsers. Same-document View Transitions were described as supported in all major browsers (as of Dec 2025) and safe to use as progressive enhancement: where they are missing, the dialog just opens without animation. However, the closedby="any" attribute, which closes the dialog on a click outside it, was not supported in Safari as of Dec 2025, so an explicit close button is still needed.
  - Quote: "To open a dialog, you call its showModal() method. This puts it on the top layer and traps focus inside. ... the closedby attribute is not supported by Safari yet (come on, Apple!). If you have a close button, I’d consider it progressive enhancement in most cases. ... They are supported in all major browsers ... Who cares if the animation is missing, the content is still there."
- Supporting prefers-reduced-motion takes one check: if matchMedia('(prefers-reduced-motion: reduce)') matches, do not assign view-transition-name. The dialog then gets the default cross-fade instead of the morph, so reduced-motion users still see a soft transition with no movement.
  - Quote: "The prefersReducedMotion check skips the view-transition-name assignment for users who prefer reduced motion. The dialog will still animate, but instead of motion, it just fades."
- By default the dialog closes instantly with no animation. To animate closing, listen for the dialog's 'cancel' event and call e.preventDefault(). Then reverse the view-transition-name handoff (dialog image back to grid image) inside document.startViewTransition(), ending with dialog.close(). The author says this works for Esc, a click outside, and close buttons. Caveat to check: under the HTML spec, calling dialog.close() directly does not fire 'cancel'. A close button only takes this path if it calls dialog.requestClose() or runs the same transition code.
  - Quote: "But wait, closing it makes it vanish instantly. To animate that, we have to intercept the event and run our own transition first ... This works for any close method, pressing Esc, clicking outside, or good old close buttons."

### web.dev

Source URLs: https://web.dev/articles/optimize-lcp

- web.dev (Google Chrome team guidance) says the LCP image must never be lazy-loaded. On a hero-led layout that image is usually the hero photo. Putting loading="lazy" on the LCP <img> always adds resource load delay and makes LCP worse.
  - Quote: "Never lazy-load your LCP image, as that will always lead to unnecessary resource load delay, and will have a negative impact on LCP."
- The LCP image is only fetched early if the initial HTML exposes it. web.dev lists three cases the browser cannot discover from the HTML: an <img> injected by JavaScript, an image lazy-loaded by a JS library that hides src/srcset as data-src/data-srcset, and a CSS background image. Any of these needs to be preloaded with a high fetch priority instead. This bears directly on how a rotating full-bleed hero is built: a real <img> in the HTML versus a CSS background or a client-side JS swap.
  - Quote: "The LCP element is an <img> that is dynamically added to the page using JavaScript. The LCP element is lazily loaded with a JavaScript library that hides its src or srcset attributes (often as data-src or data-srcset). The LCP element requires a CSS background image. ... To eliminate unnecessary resource load delay, your LCP resource should be discoverable from the HTML source."
- fetchpriority="high" belongs only on the image likely to be the LCP element. Setting it on more than one or two images stops it from helping LCP. Images that appear early in the HTML but are hidden at first, such as carousel slides that aren't visible yet, can be given a lower priority. This applies to rotating-hero and carousel designs.
  - Quote: "It's a good idea to set fetchpriority="high" on an <img> element if you think it's likely to be your page's LCP element. However, setting a high priority on more than one or two images makes priority setting unhelpful in reducing LCP. ... You can also lower the priority of images that might be early in the document response but aren't visible due to styling, such as images in carousel slides that aren't visible at startup."
- For LCP, server-rendered HTML beats client-side rendering because content can render without waiting on extra JavaScript requests. Static site generation (prerendering at build time) is described as generally the better choice for performance than on-demand SSR whenever the architecture allows it. This favors a statically generated personal site.
  - Quote: "Your page content won't require additional JavaScript requests to finish before it can render. ... A similar option to SSR is called static site generation (SSG) or prerendering. This is the process of generating your HTML pages in a build step rather than on-demand. If prerendering is possible with your architecture, it's generally a better choice for performance."
- Image CDNs shorten LCP load duration because they serve from closer locations and shrink files automatically. Hosting images on a third-party domain adds a connection cost that preconnect only partly offsets, and web.dev calls serving images from the same origin as the HTML document the best option. This matters when choosing between a host's built-in, same-origin image optimization and an external image CDN.
  - Quote: "While image CDNs are a great way to reduce resource load durations, using a third-party domain to host your images comes with an additional connection cost. While preconnecting to the origin can mitigate some of this cost, the best option is to serve images from the same origin as your HTML document."

### mux.com


- By default, every major browser (Chrome, Safari, Firefox, Edge) autoplays a muted video, but none reliably autoplays one with sound until the user interacts. So a hero or research-card teaser video needs four attributes: autoplay, muted, loop and playsinline. Without playsinline, iPhone Safari opens the video in a fullscreen player instead of playing it inline. [Extractor note: this matches Chrome's autoplay policy ('muted autoplay is always allowed') and the markup web.dev recommends for replacing GIFs (autoplay loop muted playsinline). The rule is only a default. Users can block all autoplay (Firefox 'Block Audio and Video', Safari per-site 'Never Auto-Play'), and the article itself says iOS Low Power Mode can suspend playback.]
  - Quote: "Every major browser — Chrome, Safari, Firefox, Edge — will autoplay a video that is muted. None of them will reliably autoplay a video with sound without explicit user interaction first. ... The playsinline attribute is non-negotiable — leave it out and your iPhone visitors see a fullscreen video player instead of a background loop."
- Videos further down the page, such as teaser clips on research cards in a one-page site, should not load until they are near the viewport. The recipe: start with preload="none". An IntersectionObserver with rootMargin '200px' then switches preload to 'metadata' and calls play() about 200px before the video scrolls into view. Looping videos are paused while the tab is hidden, using the Page Visibility API (visibilitychange / document.hidden), so they stop using bandwidth. The stated reason is that lazy loading stops video from competing with above-the-fold resources. The article ties this to Core Web Vitals but gives no measurements.
  - Quote: "Don't start loading a background video until it's actually in or near the viewport. ... But for secondary sections with background video further down the page, lazy loading prevents video from competing with above-the-fold resources. ... The rootMargin: '200px' starts loading the video 200 pixels before it enters the viewport, so playback starts before the user scrolls to it."
- Every autoplaying video should have a static poster image to fall back on. The poster replaces the video when: (a) the user has set prefers-reduced-motion: reduce (remove autoplay and pause through matchMedia, or hide the video with a CSS media query); (b) autoplay is blocked or suspended, for example by iOS Low Power Mode (caught by the rejected play() promise); or (c) navigator.connection reports saveData, or an effectiveType of '2g' or 'slow-2g'. That last check only works in Chromium and Android browsers. [Extractor note: the article never mentions WCAG 2.2.2 Pause, Stop, Hide (Level A). That criterion requires a way for the user to pause, stop or hide moving content that starts on its own, lasts more than 5 seconds and appears alongside other content. The article's looping, control-free pattern relies only on the OS reduced-motion setting, so a visible pause control would still be needed to meet 2.2.2.]
  - Quote: "For background video, the right behavior is to show a static poster image instead of playing the video ... Low-power mode on iOS can suspend background video playback. The right response here isn't to fight the browser — it's to have a good poster image fallback. ... Serving a poster image to visitors on 2G or with data saver enabled is the right tradeoff"
- A video section whose container has no reserved size is a common cause of Cumulative Layout Shift (CLS). The fix: give the container an explicit height or CSS aspect-ratio, and position the video absolutely (inset: 0; width/height 100%; object-fit: cover) so it stays out of document flow. A container background-color that matches the video's main tone avoids a blank white flash before the poster or video appears. (Extractor inference: for teaser-video cards, this means media boxes with a fixed aspect ratio.)
  - Quote: "Background video sections are a common source of Cumulative Layout Shift (CLS) if the container doesn't have a defined height before the video loads. Set an explicit aspect ratio or height on the container, and use position: absolute on the video element so it doesn't affect document flow"
- Animated GIF is never the right format for looping video. The article says GIFs are 10–50x larger than equivalent H.264 video (a 5-second loop of about 200KB as MP4 might be 4–8MB as GIF) and decode on the CPU. For a 10-second hero loop it gives these sizes: GIF 4–8MB; self-hosted 1080p MP4 8–15MB (about a 45-second download on 3G); low-quality HLS rendition 400–800KB; high-quality HLS rendition 2–4MB. [Extractor note: these are uncited estimates from Mux, which sells HLS hosting. web.dev's standard example shows a smaller gap: a 3.7MB GIF became a 551KB MP4 and a 341KB WebM, about 7–11x. The MP4 row is a 1080p file, while the HLS rows are lower-resolution versions (the article's own code caps HLS at max-resolution="720p"). An MP4 encoded at the same resolution and bitrate would be about the same size. HLS's real advantage is switching between versions to suit each connection, not smaller files per se.]
  - Quote: "Because the GIF format was designed in 1987, it uses an inefficient compression algorithm that produces files 10–50x larger than an equivalent H.264 video for the same visual output. A 5-second looping animation that's 200KB as an MP4 might be 4–8MB as a GIF. ... A single 1080p MP4 encoded for "web" at reasonable quality runs 8–15MB for a 10-second loop. On a 3G connection, that's a 45-second download for content that's supposed to feel instant."
